## 0. What this app is

An open-source, offline-first **habit tracker** for iOS and Android (Flutter). People build habits (check them off, count toward a goal, or log a measured amount) or quit them (every day counts as clean until you mark a slip).

**Non-negotiables**

- **No paywall, subscriptions, ads, IAPs, or feature gating — ever.** The only monetization surface is an optional "Support this project" link in Settings.
- **Local-first.** No backend, no account. All data lives in SQLite on the device.
- **Inspired by HabitKit, not a copy.** Do not reuse its assets, copy, or exact colors.

**Instructions for AI assistants**

- Make the smallest change that solves the problem; do not refactor unrelated code.
- Deliver **complete files**, one per file, with the destination path stated. Say clearly which files are new and which replace existing ones.
- After any edit, check that every symbol you used is imported (a missing import is the most common mistake in this codebase) and that brackets balance.
- You usually cannot compile. Say so when it's true, and never claim something "works" that you have not run.
- If a table changes, say so explicitly and tell the user to run `build_runner` (section 8).

## 2. State management and data flow

**Riverpod 2.x (`flutter_riverpod`), hand-written providers — no code generation.** Not Bloc, not Provider. There is no use-case layer; the repository is the boundary.

```
Drift tables ─▶ AppDatabase ─▶ HabitRepository ─▶ providers ─▶ ConsumerWidget UI
 (core/database)               (maps rows to       (Stream/        (ref.watch to read,
                                domain models)      Provider)       ref.read to write)
```

- **Reads are reactive.** Repository methods return Drift `.watch()` streams; providers expose them as `StreamProvider`; widgets `ref.watch` them and rebuild when rows change. There is no manual refresh anywhere.
- **Writes go through the repository.** UI callbacks call `ref.read(habitRepositoryProvider).someMethod(...)`. Never mutate provider state to "fake" a write; the database stream is the source of truth.
- **`ref.watch` in `build`, `ref.read` in callbacks.** Never `ref.read` in `build` to get reactive data.
- **Domain models, not Drift rows, in the UI.** The repository maps `HabitRow` -> `Habit`. Exceptions: `CompletionRow` and `NoteRow` are used directly as stream element types.

### Provider inventory

| Provider | Kind | Purpose |
|---|---|---|
| `appDatabaseProvider` | `Provider<AppDatabase>` | The single DB instance (closed on dispose) |
| `habitRepositoryProvider` | `Provider<HabitRepository>` | Entry point for all writes |
| `activeHabitsProvider` | `StreamProvider<List<Habit>>` | Non-archived habits, ordered by `sortOrder`, with `categoryIds` |
| `archivedHabitsProvider` | `StreamProvider<List<Habit>>` | Archived habits |
| `habitCompletionsProvider(habitId)` | `StreamProvider.family<List<CompletionRow>, String>` | Every logged day for one habit |
| `todayCompletionsProvider` | `StreamProvider<Map<String, CompletionRow>>` | Today's rows keyed by habit id |
| `habitNotesProvider(habitId)` | `StreamProvider.family<Map<String, NoteRow>, String>` | Notes keyed by `yyyy-MM-dd` |
| `categoriesProvider` | `StreamProvider<List<Category>>` | All categories |
| `themeSettingsProvider` | `StateNotifierProvider<…, ThemeSettings>` | Palette + light/dark/system |
| `cardSizeProvider` | `StateNotifierProvider<…, HabitCardSize>` | Today card size |
| `initialCardSizeProvider` | `Provider<HabitCardSize>` | Overridden in `main()` with the saved value |

### Two kinds of persisted state

1. **Domain data** → Drift (SQLite). Everything about habits.
2. **Small UI preferences** → `shared_preferences`, behind a `StateNotifier` (theme palette/mode, Today card size) or a tiny static helper (`OnboardingStorage`). Keys: `theme_palette`, `theme_mode`, `today_card_size`, `onboarding_completed`.

### Startup sequence (`main.dart`)

1. `WidgetsFlutterBinding.ensureInitialized()`.
2. Read the onboarding flag and the saved card size **before the first frame**, so there is no flash of the wrong screen or size.
3. Build `createAppRouter(initialLocation: onboardingDone ? '/today' : '/onboarding')`.
4. `runApp(ProviderScope(overrides: [initialCardSizeProvider…], child: HabitTrackerApp(router: …)))`.

(The theme provider still loads asynchronously after start; a brief default-theme flash is a known, accepted gap.)

### Navigation

`go_router`, built by `createAppRouter()` (each call makes its own root navigator key).

- **Tabs** (inside a `ShellRoute` with the custom bottom bar): `/today`, `/habits`, `/insights`, `/settings`.
- **Full-screen routes** (root navigator, cover the bottom bar): `/onboarding`, `/habits/new`, `/habits/edit`, `/habits/detail`.
- `/habits/edit` and `/habits/detail` receive the `Habit` through `extra`. `/onboarding` takes `extra: true` for a replay (finishing just pops).
- **Pickers use plain `Navigator.push(MaterialPageRoute)` and return a value** (`IconPickerScreen` -> icon id/emoji, `CategoryPickerScreen` -> `List<String>`). Don't turn these into routes.
- `HabitDetailScreen` receives a snapshot via `extra` but **re-resolves the live habit** from the providers every build, so edits show immediately.

## 3. Data model rules

**Schema version 3.** Tables: `Habits`, `Completions`, `Categories`, `HabitCategories` (join), `Notes`, `Reminders` (unused).

- **Dates are `yyyy-MM-dd` text**, produced and parsed only by `DateOnly`. No timestamps for "which day" questions.
- **One `Completions` row per (habit, date)** (unique key). Upsert, never duplicate.
- **Build habits:** no row = not done. **Quit habits:** no row = clean; a slip is a row with `isSlip = true` (value 0). Streaks and heatmaps follow this.
- **Amounts are stored as integers.** Yes/No and Count store plain numbers (Yes/No done = `targetPerDay` = 1). **Measure stores thousandths** (2.5 L -> 2500), and its goal (`targetPerDay`) and `tapIncrement` are scaled the same way. Always go through `Habit.formatAmount` / `parseScaledAmount` / `formatScaledAmount`; never hand-scale.
- **"Good day" is always `value >= targetPerDay`** (build) or `no slip` (quit). Because amounts are integers, heatmaps, streaks, and the calendar share one rule and need no special cases per tracking method.
- **`Habit.tracksAmount`** = build habit whose `trackingMethod` isn't Yes/No. Only these show the progress pill and amount dialogs. Quit habits are always Yes/No.
- **The `trackingMode` column means "what a tap does"** for Count/Measure: `stepByStep` = add `tapIncrement`; `customValue` = ask for the day's total. (Name kept for older data.)
- **Changing a build habit's tracking method rewrites its history** inside one transaction (`HabitRepository._convertHistoryForMethodChange`); the edit screen confirms first. Don't bypass `updateHabit` for this.
- **Backfill window:** a calendar day is editable only if it is today or within `editableWindowDays` (14) days back, on/after the habit's creation date, and not in the future.
- **Streaks:** floor at the habit's `createdAt` (the loop must always terminate). A build habit's *unlogged today* does not break an otherwise intact streak; a quit slip today does.
- **Dates before a habit existed** are never "clean", "missed", or editable — they render as neutral gray.
- **`toggleToday`** is a legacy name; it toggles any `date`.

## 4. Theme and styling rules

### Never hardcode colors or fonts in screens

Read everything from `Theme.of(context)`: `colorScheme.*`, `textTheme.*`, `dividerColor`. The only per-item color that is allowed is **a habit's or category's own color** (`hexToColor(habit.color)`), used for identity (avatar tint, heatmap dots, list accent stripe, category tags).

`ColorScheme.fromSeed()` is **banned** — it produces the washed-out default Material look. All four schemes in `color_schemes.dart` are hand-built.

### Color roles (use the role, not the hex)

| Role | Use for |
|---|---|
| `primary` | Active nav item, checkmarks / completed button, progress fill, success, primary buttons |
| `secondary` | The single "pop" accent — the floating add button |
| `tertiary` | **Streak and milestone icons** (the flame) — in both palettes |
| `primaryContainer` | Tinted icon tiles and info boxes |
| `secondaryContainer` | Selected-option backgrounds (e.g. the chosen theme card). **Not** habit-card completion — cards are never tinted by state |
| `surface` | Scaffold and cards |
| `surfaceContainerHigh` | Inputs, chips, elevated panels |
| `outlineVariant` = `theme.dividerColor` | All borders and dividers |
| `onSurfaceVariant` | Secondary text, captions, inactive icons |

Prefer `onPrimary` over `Colors.white` for content on a primary fill (a few older spots still use white).

### Typography (Google Fonts)

- **Fraunces** (serif, character) for display and titles: `displayLarge` 40, `headlineLarge` 30, `headlineMedium` 24, `headlineSmall` 20, `titleLarge` 20, and app-bar titles.
- **Inter** for everything else: body text, `titleMedium` (16, w600), `labelLarge` (13, w600).
- Use the `textTheme` slots with `copyWith` for small tweaks; don't introduce new font families or ad-hoc sizes where a slot fits.

### Component and layout rules

- **Habit cards:** surface fill + `dividerColor` border, **identical whether or not the habit is done**. Completion is shown by the track button only (check square, or the progress pill for Count/Measure).
- **Today card sizes** (`HabitCardSize`, remembered across launches): padding 12/16/18, corner radius 16/20/22, gap between cards 8/14/16 for Small/Medium/Large. Medium is the default. Small = name + one-week strip + streak; Medium = description + heatmap + streak footer; Large = bigger heatmap with month labels + category tags + stats row.
- **Radii:** inputs 14, buttons 16, avatar tile `size × 0.28`, heatmap cell `cell × 0.3`. **Track button:** 36 px tall.
- **Heatmap color rule — one function: `heatmapDayColor()`.** Habit color = goal met / clean; the same color at a partial opacity (`partialProgressAlpha`: faint 0.1 at rest, 0.28→0.80 as a Count/Measure day nears its goal) = tracked but short; neutral `outlineVariant @ 0.5` = can't be tracked (before creation, or future). Day cells are **always visible** — never `Colors.transparent` for in-range days.
- **Heatmap layouts:** weeks as columns, Mon–Sun as rows, current week on the right, sized to the available width (no fixed heights).
- **Headers** are left-aligned (themed `AppBar`); the bottom bar is custom, with a small underline for the active tab.
- Use **`withValues(alpha: …)`**, not `withOpacity`.

## 5. Coding conventions

**Language and style**

- Strict null safety. Avoid `!`; use `?.`, `??`, local null checks, or restructure so the analyzer can promote. Check `x != null` **in the same condition** you dereference it (a bool computed earlier does not promote).
- Strong typing: declare return types (`always_declare_return_types`), no `dynamic`, use records for small tuples (`({int value, bool isSlip})`), `enum`s for closed sets.
- **`const` constructors and `const` widgets wherever possible.** Mark `final` fields.
- Single quotes, trailing commas, no `print` (lints enforced in `analysis_options.yaml`; generated `*.g.dart` is excluded).
- Files `snake_case.dart`; private helpers `_prefixed`; one main public concept per file.

**Widgets**

- Keep widgets small and single-purpose. A widget used by one screen is a private class in that screen's file; promote it to `widgets/` only when a second place needs it.
- Prefer `ConsumerWidget` / `ConsumerStatefulWidget`; use plain `StatelessWidget` for pure presentation with no providers.
- Controllers (`TextEditingController`, `ScrollController`, `PageController`) are created in `State` and disposed in `dispose()`.
- Use `late` for fields that read `widget.*` in their initializer.
- Check `mounted` before using `context` after an `await`.
- Comments explain **why**, not what. Doc-comment (`///`) public classes and any non-obvious rule.

**Data layer**

- Drift table classes are plural; **every table gets `@DataClassName('XRow')`** so its generated row class can never collide with a domain class (`Habit`, `Category`, …).
- Never name a Drift column `text` (collides with the `text()` builder).
- A reactive stream that needs data from two tables must **watch both tables** — Drift only tracks tables referenced by the query you call `.watch()` on. See `_watchHabitsWithCategories`.
- Multi-step writes go in `_db.transaction`.
- Add new columns with a default (or nullable) **and** a migration step **and** a `schemaVersion` bump — `onCreate` alone only covers fresh installs.
- Persist enums by `.name` and parse with a `fromName` that falls back safely.

**Dates**

- Use `DateOnly` for every day key. Build dates with `DateTime(y, m, d + n)`, **not** `date.subtract(Duration(days: n))` (breaks across daylight-saving changes).

**Layout (lessons paid for in bugs)**

- A `Row` with `CrossAxisAlignment.stretch` overrides children's own width/height — wrap fixed-size children (`HabitAvatar` does this itself).
- Put padding **inside** a fixed-width box, not around a `Row` whose parent width is fixed; outer padding adds width and overflows.
- Don't give a grid a fixed height; let cell size derive from width.
- `DropdownButton` with multi-line items needs `itemHeight: null`.
- Scrollable pages should tolerate small screens and large fonts (`SingleChildScrollView` + `ConstrainedBox(minHeight)`), never a fixed-height Column.
- Anything that can loop backwards in time needs a floor.

**Process**

- When a new file is needed, put it in the existing feature structure above and state its path.
- New user-facing settings: model field -> table column (+ migration) -> repository method -> UI -> persist -> update this file.

## 6. Build, run, and environment

```
flutter pub get
dart run build_runner build --delete-conflicting-outputs   # after ANY table change
flutter run
```

- If the generated names look stale (`type not found`, ambiguous imports), delete `lib/core/database/app_database.g.dart` and run build_runner again.
- Use `dart run build_runner …`, not a bare `build_runner …`.
- Don't add `riverpod_generator`/`riverpod_annotation`; they conflict with the `build_runner` version Drift needs, and the app uses hand-written providers.
- Windows, project and pub cache on different drives: if Gradle's Kotlin daemon throws "this and base files have different roots", add `kotlin.incremental=false` to `android/gradle.properties`.
- Android emulator "INSUFFICIENT_STORAGE": wipe its data or raise its internal storage in the AVD settings.
- Android needs core library desugaring (`flutter_local_notifications`): `isCoreLibraryDesugaringEnabled = true` and `desugar_jdk_libs` in `android/app/build.gradle.kts`.

## 8. Checklists

**Add a column to a table**
1. Add the column with a default (or nullable) in `core/database/tables/*.dart`.
2. Bump `schemaVersion` and add an `if (from < N) { await m.addColumn(...); }` step in `app_database.dart`.
3. Update the domain model, the repository mapping (the stream and any create/update), and any `copyWith`.
4. Run `build_runner`.

**Add a screen**
1. Create it under `features/<feature>/presentation/screens/`.
2. Register the route in `createAppRouter()` (root navigator key for full-screen routes).
3. Pass models through `extra`; re-resolve live data from providers if edits can happen while it's open.

**Add a setting that must survive restarts**
1. Small preference: a `StateNotifier` + `shared_preferences`; if it affects first paint, preload in `main()` and override an `initialXProvider`.
2. Per-habit data: a column, not a preference.

**Add a theme palette**
1. Add a value to `AppThemePalette` (label + description).
2. Build its light and dark `ColorScheme`s in `color_schemes.dart` (hand-picked, including `tertiary`, `secondaryContainer`, and `outlineVariant`).
3. Map it in `AppTheme._schemeFor`.
